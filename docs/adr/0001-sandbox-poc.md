# 0001：优先验证 OpenSandbox 动态执行面

- 状态：接受（仅限 PoC 路线；生产选型待实测）
- 日期：2026-10-10
- 依据：用户确认任务主要为 Agent 动态代码、命令与浏览器操作，并要求继续下一步。

## 决策

将沙箱作为 MVP 核心组件，优先验证 OpenSandbox Docker 后端。
使用 Python 3.12 和固定版本 SDK 编写独立验证脚本；这不决定控制服务和 Runner 的实现语言。
Agent Runtime、模型网关、Hatchet/Temporal 保持待决。
先固定工具 fixture 验证执行环境，再接入模型驱动循环，避免将模型输出不确定性与环境故障混在一起。

## 边界

控制面、Runner、沙箱管理面属于受管基础设施。任务沙箱运行动态代码、命令与浏览器。
如果上传的 Agent 程序不可信，Agent 本身也放进独立隔离环境，不能继承 Runner 凭证。
工具请求绑定 task_id、attempt_id、execution_epoch 和 sandbox_id；跨代次不得共享可写工作区或浏览器会话。
第一期本机执行不直接复用宿主 Shell、日常浏览器 Profile 或登录会话。

## 备选与代价

直接封装 Docker 可减少一个管理服务，但需要自行构建生命周期、执行、文件和浏览器接口。
OpenSandbox 提供这些接口的集成起点；仍需验证隔离、回收和 SDK/Server 升级兼容性。
微虚拟机留作后续更强隔离候选；容器方案通过 PoC 不等于适合全部不可信多租户负载。

## 验证与退出条件

见 [PoC 操作说明](../../poc/sandbox/README.md) 与 [验收矩阵](../sandbox-poc.md)。
尚未真实运行，无吞吐、隔离强度或生产可靠性结论。
若网络、取消/回收、浏览器资源限制无法满足底线，不降低验收标准；评估底层运行时或替代沙箱方案。
